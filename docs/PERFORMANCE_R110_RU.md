# FPS: r109-r111

30 сентября 2026. Испытан один Samsung Galaxy S7 SM-G930F.
Стабильные 60 FPS для любого приложения пока не подтверждены.

## Установлено

- Monitor 0.3.32.0, пакет 2026093007. Телефон подтвердил совпадение с ПК.
- BOOT и установочный диск содержат тот же согласованный пакет.
- Камера, Sniper, звук и ядро в этих изменениях не переделывались.
- IddCx 1.9 используется при сборке. Минимум 1.4 сохранён.
  Запрос GPU-приоритета защищён проверкой доступности API и восстановлением.
- После `E_PENDING` активный захват повторяется через точный таймер 2 мс.
  После 100 мс без активности интервал увеличивается до 50 мс.
  Глобальное разрешение таймеров Windows не меняется.

Старая обычная задержка 16 мс иногда занимала около 32 мс. В r110 эта
длинная пауза не воспроизвелась. Это частичное исправление, не гарантия FPS.

## Управляемый источник

Для дальнейшей отладки используется тестовая анимация на S7. Каждый кадр
имеет свой двоичный номер и контрольное дополнение. Частота источника задана
точным таймером. Обычное видео и ручные действия пользователя не нужны.

120-секундный источник сформировал 60,00002 Present/s. Вложенный интервал
телефонных счётчиков составил 111,8608 с:

| Стадия | Кадры | FPS |
| --- | ---: | ---: |
| Приём | 6710 | 59,985 |
| Декодирование | 6710 | 59,985 |
| Запрос вывода | 6675 | 59,672 |

В журналах драйвера было около 300 новых номеров за каждые 5 секунд,
без пропусков и повторных номеров в этих окнах. CPU readback и ожидания
GPU allocator равны нулю. Decoder retries и транспортные drops не выросли.
SoC оставался 40 C. Это не измерение физической частоты панели.

На телефоне за тот же интервал декодер отбросил 7 готовых кадров,
очередь вывода заменила 20 ожидающих кадров и отклонила 7 по возрасту.
Пограничные кадры и неатомарность снимков мешают свести счётчики до единицы.
Отставание вывода не скрывается округлением до 60.

## Ограничения проверки

- На обычном видео в r110 сохранялись окна 50,4-59,6 FPS на выводе.
- При активном окне S7 спад до 47 FPS тоже воспроизвёлся. Фокус окна
  не установлен как причина. Частоты остальных мониторов не менялись.
- Отдельная трасса сопоставила 1675 номеров кадров из статистики
  DirectComposition S7 с IddCx: все эти номера были получены драйвером.
  Это локализует потери в том прогоне, но не устанавливает причину внутри ОС.
- API Present, callback WGC и новый номер кадра не равны доказательству
  уникального физического изображения. Проверка счётчика в пикселях проведена
  в отдельных коротких прогонах. WGC-наблюдатель тоже пропускал кадры.
- Смена политики Present у тестового источника меняла результат. Поэтому
  один короткий синтетический прогон не является приёмкой всего продукта.

## Сборка

Приватная Windows x64 сборка и целевые тесты прошли. Дополнительная сборка
IddCx 1.4 тоже прошла. Очищенный Monitor x64 собран с фиктивным серийником,
`/W4 /WX`, проверкой INF и созданием каталога. Он не подписан и не установлен.
Известные ограничения полного набора тестов из аудита r103 сохраняются.

Диагностические программы и трассы не запускаются установщиком. Прогоны
ограничены по времени; видео не записывается. Сырые журналы, снимки, серийник,
локальные пути, подписанные пакеты и ключи в репозиторий не добавляются.

Документация API:
[Compositor clock](https://learn.microsoft.com/en-us/windows/win32/directcomp/compositor-clock/compositor-clock),
[IddCx metadata](https://learn.microsoft.com/en-us/windows-hardware/drivers/ddi/iddcx/ns-iddcx-iddcx_metadata).

## r111: очередь декодированных кадров

В BOOT r111 декодер передаёт готовую серию кадров в существующую ограниченную
очередь вывода. Раньше `DrainLatest` отбрасывал кадры ещё до этой очереди.
Размер очереди, лимит возраста и владение DMA не увеличены. Старый прямой
путь без очереди сохраняет прежнее поведение. Windows-пакет остаётся r110.
BOOT записан с обратной проверкой SHA-256; пакет и диск на телефоне проверены.

Новый тест серии из двух DMA-кадров падал до изменения. После него прошли
три запуска целевых race-тестов декодера, очереди и DECON. Обе ARM64-сборки
скомпилированы. В более широкую выборку попал падающий тест
`TestTorchWorkerCancellationClosesDriver`; он не вызывает изменённый декодер.
Полный набор тестов не объявляется исправным.

Повтор с тем же бинарником анимации: источник 59,99992 Present/s. За 112,0741 с
S7 принял и декодировал 6479 кадров, запросил вывод 6452. Раннее отбрасывание
декодером равно нулю. Очередь заменила 8 кадров, отклонила 18 по возрасту.
Ошибок USB и перезапусков декодера нет; SoC 40-41 C.

При этом захват Windows в начале повтора снова давал около 47 FPS, затем
приблизился к 60. Источник всё это время держал 60 FPS. Поэтому основной
провал воспроизводится без браузера и без видео. Предыдущий успешный прогон
нельзя считать исправлением захвата. Средние FPS двух прогонов не являются
честным сравнением скорости прошивок: входной темп различался.
