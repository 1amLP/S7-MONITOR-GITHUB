# Monitor r104-r108: изменения и проверка

30 сентября 2026. Один Samsung Galaxy S7 SM-G930F / Exynos 8890.
Windows 11 x64, NVIDIA RTX 3060. Это продолжение [аудита r103](AUDIT_R103_RU.md),
не заявление о полной оптимизации и не приёмка всех устройств.

## Что установлено

- Windows Monitor 0.3.30.0, подписанный пакет 2026093005.
- Ядро `3.18.140-g3dfe42cdf48c`; исправление DWC3 сохранено.
- BOOT, архив Windows и образ установочного диска записаны на телефон.
  Хеши прочитаны обратно. Windows установил пакет с телефона без перезагрузки
  ПК. Телефон подтвердил совпадение пакета.
- Бинарники Camera и менеджера, включая Sniper, сохранены из принятой версии.
- Общие USB-таймауты, thermal/watchdog и зарядка 50/80 не ослаблялись.

## Изменения

### ПК

Monitor передаёт аппаратному H.264 MFT удерживаемые D3D11 NV12-поверхности.
Убраны staging-readback NV12 и повторное полное копирование в новый MF buffer
на каждом кадре. Пул ограничен шестью samples. Пока MFT или очередь владеет
sample, поверхность не используется повторно. Обновление статичного кадра
получает отдельные временные метки и сохраняет владельца пикселей.

При несовместимом GPU/MFT сохранён прежний путь через память. Sniper пока
использует прежний readback и shared memory. Нельзя переносить утверждение
«ноль CPU-копий» с Monitor на Sniper или выход виртуальной камеры.

Повтор получения кадра при отсутствии уведомления ограничен 16 мс вместо
50 мс во время передачи. Это соответствует циклу ожидания в
[образце Microsoft IddCx](https://github.com/microsoft/Windows-driver-samples/blob/main/video/IndirectDisplay/IddSampleDriver/Driver.cpp).
Добавлены счётчики уведомлений, таймаутов, кадров после таймаута и длительности
GPU-конвертации/FinishedProcessingFrame. Настройки GPU Windows не меняются.
Одно сокращение таймаута не доказывает причину всех прежних провалов.

### Телефон

Декодер просыпается при получении сжатого кадра, смене поколения и возврате DMA.
При незавершённой работе проверка идёт через 2 мс, без работы через 250 мс.
Первый IDR сохраняется при смене поколения. Зависимые H.264 AU не заменяются
более свежими сжатыми кадрами.

В MFC синхронизируется занятая часть сжатого H.264 OUTPUT-буфера (`bytesused`),
а не вся ёмкость 1 МиБ. Использованы существующие exact-хелперы старого ядра.
RAW/NV12 CAPTURE, DRM и энкодер камеры не менялись. Изменение атрибутов ION
для всего NV12 отвергнуто: оно не следовало фактическому пути этого ядра.

Исправлена гонка установочного канала. ПК мог прислать следующий запрос
после получения ответа, но до возврата write на телефоне. Старый busy-флаг
терял запрос. Теперь одна следующая команда может ждать завершения записи;
очередь ограничена. Две новые загрузки полного пакета r105 прошли за 187/163 мс
с совпадающим SHA-256. Автообновление r106 также завершилось успешно.

## Замеры

Условия: Monitor 1280x720, 60 Гц, ECO включён, меню закрыто. Настройки разрешения
и ECO между этими окнами не менялись. Часы телефона и ПК не совпадали, поэтому
длительность окон считалась по монотонным часам ПК, а не разнице UTC устройств.
Снимки счётчиков не атомарны относительно часов ПК; значения FPS приблизительны.

| Сценарий | Окно | Получено/с | Передано на вывод/с |
| --- | ---: | ---: | ---: |
| r103, оставленное пользователем видео | 60,75 с | 55,52 | 55,39 |
| r105, видимое синтетическое движение | 20,28 с | 59,82 | 59,48 |
| r105, повторный короткий интервал | 6,24 с | 51,42 | 51,42 |
| r105, движение + Front 720p30 | 6,22 с | 59,85 | 59,37 |
| r106, видимое движение, прогон 1 | 20,19 с | около 60 | 59,59 |
| r106, видимое движение, прогон 2 | 20,15 с | около 60 | 59,91 |
| r106, обычное видео пользователя, окно 1 | 20,16 с | 50,15 | 50,15 |
| r106, обычное видео пользователя, окно 2 | 20,27 с | 56,55 | 56,55 |
| r106, обычное видео пользователя, окно 3 | 20,14 с | 46,02 | 45,97 |
| r106, то же видео в оконном режиме | 30,22 с | 44,00 | 44,04 |

В r106 окно теста проверило своё положение на S7, видимость и отсутствие
occlusion. Источник отправлял около 75 Present/s. Это частота API источника,
не 75 обновлений экрана телефона. Драйвер получал около 300 новых кадров
за 5 секунд: пропуски PresentationFrameNumber и повторные номера равны нулю.
CPU NV12 readbacks и ожидания allocator равны нулю после запуска.

Средняя длительность вызова GPU-конвертации: 0,14-0,18 мс. Это время CPU-вызова
и постановки GPU-команд, не GPU timestamp query. Число перезапусков декодера
не выросло ни в одном из двух прогонов. Во время замены драйвера был один
автоматически восстановленный timeout декодера; скрывать его нельзя.

SoC в обоих прогонах r106: 40 C. CPU по снимкам: 15-22%. Это не сравнение
теплового равновесия при одинаковой длительной нагрузке. Снижение температуры
на определённое число градусов не доказано. Thermal pause не наблюдалась.

На обычном видео после этих тестов провалы воспроизвелись. SoC оставался
40 C, новых перезапусков декодера и обрывов USB не было. При спаде Windows
передавал драйверу лишь 223-252 новых кадра за 5 секунд, GPU-конвертация
занимала около 0,15 мс на вызов. Приём и вывод телефона почти совпадали.
Значит, сокращение ожидания до 16 мс не исправило реальное воспроизведение.
Разделение потерь между плеером, DWM и выдачей IDD требует следующего замера;
одни счётчики драйвера не устанавливают причину внутри Windows.
Снимок статистики YouTube после этого показал 2560x1440@60, один dropped
frame из 11730 и буфер 24,25 с. Массовой потери кадров декодером плеер не
сообщает. Активные дисплеи проверены через DisplayConfig: 120, 75, около 60
и ровно 60 Гц для S7. Связь провалов с разными частотами пока только гипотеза;
частоты, DPI, реестр и настройки браузера не менялись.
Выход из fullscreen не устранил спад: в 30-секундном окне получено около
44 FPS на всех стадиях. Новых decoder retries не было, SoC оставался 40 C.

Front 720p30 вместе с Monitor в r105: 297 кадров за 10 секунд, 29,77 FPS,
три пропуска на стороне источника. USB backpressure/retry равны нулю,
после теста камера остановилась. Строгий тест без пропусков не пройден.
Тесты не сохраняли видео.

## Проверки и ограничения

- Приватная сборка Windows x64 с /W4 /WX и тесты протокола, очередей,
  владения I/O, NV12, камеры и Sniper прошли.
- GPU NV12-тест на реальной видеокарте прошёл для 720p и 1440p: цвет BT.709,
  выход H.264, удержание поверхностей и повторный IDR статичного кадра.
- Целевые Go race-тесты декодера, событийных пробуждений и очереди пакета прошли.
  Известные падения полного набора из аудита r103 не устранены этим изменением.
- Ядро собрано; прежние предупреждения section mismatch/FIPS остаются.
  Патч проверен обратным применением к зафиксированному дереву.
- Очищенный репозиторий собран для Windows x64 и Linux ARM64 с фиктивным
  серийником. Эта обезличенная сборка не прошивалась и не подписывалась.
- Пользователь подтвердил нормальное изображение после r105. Физическая
  частота матрицы и полная задержка host-to-panel не измерялись.
- Пользователь сообщил об успешном звонке WhatsApp на r103. В сохранённой
  сессии камеры 7019 кадров дошли до очереди USB, source gaps/backpressure = 0.
  Это не многочасовой звонок на новом пакете r106.
- Два коротких прогона около 60 FPS не означают исправление реального видео:
  в минутной проверке пользователя сохраняются окна 46-56,5 FPS. Также
  не пройдена длительная приёмка 1440p и полной совместной нагрузки.
- Не проверен отдельный холодный старт полностью статичного рабочего стола
  при переключении начального CPU snapshot на GPU-input MFT.
- Нужны дальнейшие проверки реального контента, нагрева и оставшихся пунктов
  аудита. Метка «максимально оптимизировано» или «production ready» неверна.

Личные серийники, сырые журналы, изображения камеры, подписанные бинарники
и ключи в этот репозиторий не добавлялись.

## Дополнительные проверки r106-r108

Источник с попарно одинаковыми изображениями и 75 Present/s дал около
60 кадров/с на приёме S7. Гипотеза об автоматическом удалении одинаковых
изображений Windows на этом синтетическом пути не подтвердилась.

После ограничения того же источника до 60 Present/s без изменения экранов
проблема воспроизвелась без YouTube: 59,77 Present/s у источника и 46,35 FPS
на приёме S7. Таким образом, прежний тест с 75 Present/s недостаточен для
приёмки потока 60 FPS. Частоты остальных дисплеев пользователь запретил
менять; они не менялись.

PresentMon 2.6.0 из официального релиза Intel/GitHub, с проверенной подписью
и SHA-256, использовался в двух ограниченных сессиях. Он не показал полного
потока кадров видео Chrome. По этим неполным данным нельзя объявлять причиной
декодер браузера. Изображения, ввод и видео не записывались; служба PresentMon
не устанавливалась, обе сессии завершились.

В r107 только виртуальный адаптер S7 получил предпочтение энергоэкономичного
GPU с аппаратным H.264 через IddCxAdapterSetRenderAdapter. Intel UHD 770
предварительно прошёл синтетический GPU-тест 720p/1440p: BT.709, 121 кадр,
три IDR. Windows действительно назначил Intel для S7. Другие дисплеи не
перенастраивались. Однако fixed60-тест дал лишь 44,72 FPS на приёме.
Выбор другого GPU не устранил провал и отклонён.

r108 / Monitor 0.3.30 возвращает обычный выбор GPU Windows.
Рабочий Driver.cpp совпадает с r106; политика выбора Intel не включена.
Версия повышена для штатной замены установленного 0.3.29. Кандидат собран,
контракты Windows прошли. BOOT, архив пакета и установочный диск записаны
с проверкой SHA-256. Пакет 2026093005 установлен с телефона; совпадение
подтверждено телефоном, в журнале снова NVIDIA RTX 3060. Перезагрузка ПК
не требовалась. Camera и менеджер сохранены без изменений.

На r108 выполнен отдельный 20-секундный timing-only тест Windows Graphics
Capture через CreateForMonitor только для S7. Он получил 940 callbacks,
около 46,99 FPS по времени поступления и PTS, без нарушения монотонности.
Во вложенном 15-секундном интервале текущий IDD-путь телефона получил
49,07 FPS и вывел 49,01. Окна разной длины; это не точное покадровое сравнение.
WGC также не дал 60 FPS. Пиксели не читались на CPU, уникальность изображений
не проверялась, видео не сохранялось. Сессия и тестовый процесс закрылись.
Новый путь WGC не добавлялся в рабочий драйвер или пакет.

Итог: оптимизации памяти и пробуждений установлены. Проблема прохождения
источника 60 FPS через композицию/выдачу Windows остаётся открытой.
Заявлять устранение FPS-провалов или гарантированное снижение нагрева нельзя.
